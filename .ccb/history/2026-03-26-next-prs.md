### PR #2512 — `fix: disable SDK built-in retries to prevent stacking with chat_with_retry`
**URL:** https://github.com/HKUDS/nanobot/pull/2512  
**Files:** `nanobot/providers/openai_compat_provider.py`, `nanobot/providers/anthropic_provider.py`, `nanobot/providers/base.py`, `nanobot/agent/loop.py`  
**What:** OpenAI SDK (`max_retries=2`) and Anthropic SDK (`max_retries=2`) stack with nanobot's `chat_with_retry` (3 retries), causing up to 12 requests per transient failure and ~10 min silent hangs.

Changes to make:
1. **`openai_compat_provider.py`** — pass `max_retries=0` and `timeout=httpx.Timeout(180.0, connect=10.0)` when constructing `AsyncOpenAI`.
2. **`anthropic_provider.py`** — same: `max_retries=0`, `timeout=httpx.Timeout(180.0, connect=10.0)` on `AsyncAnthropic`.
3. **`providers/base.py`** — add `on_retry: Callable[[int, int], None] | None = None` parameter to both `chat_with_retry` and `chat_stream_with_retry`. Call it as `on_retry(attempt, total_attempts)` before each retry sleep.
4. **`agent/loop.py`** — pass an `on_retry` callback to `chat_with_retry` / `chat_stream_with_retry` that calls `self._on_progress(f"Retrying... (attempt {attempt}/{total})")` (or equivalent progress surfacing).

**Risk:** Medium — touches provider construction and retry signature. The `on_retry` callback is additive (callers not passing it are unaffected).  
**Tests:** Add `tests/providers/test_provider_retry.py` with 3 tests:
- `on_retry` called with correct `(attempt, total)` on transient errors
- `on_retry` NOT called when first attempt succeeds
- `on_retry` works with `chat_stream_with_retry` variant

Also update `tests/providers/test_custom_provider.py` to assert `AsyncOpenAI` is constructed with `max_retries=0` and the explicit timeout.

**Caution:** We do NOT have `litellm_provider.py` (deleted in the main merge) — skip any changes to it. Our provider is `openai_compat_provider.py`.

### PR #2506 — `fix(heartbeat): prevent token explosion and session history leaks`
**URL:** https://github.com/HKUDS/nanobot/pull/2506  
**Files:** `nanobot/agent/loop.py`, `nanobot/session/manager.py`, `nanobot/cli/commands.py` (gateway heartbeat)  
**What:** Fixes two bugs that cause heartbeat sessions to accumulate tokens unboundedly:

1. **`loop.py` `_save_turn` bug** — The slice index is off by one; the initial user prompt is skipped when saving direct turns. This breaks `retain_recent_legal_suffix` truncation because it can't find user-turn boundaries. Fix: correct the `skip` index passed to `_save_turn` for direct turns so the user prompt IS included.

2. **`session/manager.py` — add `prune_by_content_length(max_chars: int)`** — A new method on `Session` that iterates over messages and truncates any individual message's text content to `max_chars` characters. This is used as a budget guard before/after heartbeat runs.

3. **`cli/commands.py` gateway heartbeat loop** — Apply both pre- and post-run cleanup:
   - Before each heartbeat run: call `session.prune_by_content_length(4000)` + `session.retain_recent_legal_suffix(keep_recent_messages)` 
   - After each run: same cleanup pass

**Risk:** Medium — touches session save logic. The `_save_turn` fix changes existing behavior for direct turns. Read the current `_save_turn` implementation in `loop.py:873` carefully before editing.

**Current `_save_turn` signature** (line 873 of `loop.py`):
```python
def _save_turn(self, session: Session, messages: list[dict], skip: int) -> None:
```
The `skip` argument controls how many leading messages to exclude from the persistent save. For direct turns, the off-by-one causes the user message to be skipped. Check the three call sites at lines 577, 627, 657 to understand the correct `skip` value for each.

**Tests:** Add regression tests in `tests/agent/` that:

- Verify message count stays bounded after `prune_by_content_length`
- Verify user prompt is correctly saved in direct turns (check `_save_turn` slice)

### PR #2508 — `feat(telegram): coalesce forwarded messages with user text`
**URL:** https://github.com/HKUDS/nanobot/pull/2508  
**File:** `nanobot/channels/telegram.py`, `tests/channels/test_telegram_channel.py`  
**What:** When users forward a message to the bot and add text (e.g. "summarize this"), Telegram sends them as two separate updates. Add an 80ms debounce to coalesce them into one agent turn.

Changes to `telegram.py`:
1. Add constant: `FORWARD_DEBOUNCE_MS = 80`
2. Add helper `_get_thread_id(msg) -> int | None` — returns `message_thread_id` or `None`
3. Add helper `_resolve_debounce_lane(msg) -> str` — returns a key like `"{chat_id}:{thread_id}"` for buffer isolation per forum topic
4. Add `_debounce_buffers: dict[str, asyncio.Task]` to `__init__`
5. Add `_enqueue_debounce(lane: str, msg, companion_text: str | None)` — stores the forward in a buffer dict, schedules `_flush_debounce(lane)` after 80ms
6. Add `_flush_debounce(lane: str)` — merges buffered forward + any companion text into one `InboundMessage`, calls `self.bus.publish(...)`
7. Modify `_on_message`: if `msg.forward_origin` is set, call `_enqueue_debounce`; also implement "reverse companion" — if a plain text arrives within 80ms of a queued forward for the same lane, absorb it
8. Modify `_flush_media_group`: route output through debounce for forward detection
9. In `stop()`: cancel all pending debounce tasks

**Important constraints for our codebase:**
- Commands (`/start`, `/new`, `/stop`, etc.) always bypass debounce — check `_forward_command` usage
- Non-forwarded media (photos, voice, documents) bypass debounce — sent immediately
- Buffer key MUST include `message_thread_id` for forum topic isolation (we already have topic support)
- `asyncio.current_task()` identity check in `_flush_debounce` to prevent double delivery

**Tests to add** (11 new in `test_telegram_channel.py`):
- Forward + text coalesced (forward arrives first)
- Text + forward coalesced (reverse companion — text arrives first)
- Forward buffered for 80ms (not delivered immediately)
- Text-only gets 80ms forward companion window
- Non-forward media bypasses debounce
- Companion text joins media_group buffer (album + text = one turn)
- Commands not absorbed by companion detection
- Forum topics isolated (different thread_ids → separate buffers)
- `stop()` cleans up debounce state without flushing

**Risk:** Medium-high — significant addition to `telegram.py`. Read the existing `_flush_media_group` and `_on_message` carefully before editing. Our `telegram.py` already has topic-aware code (`message_thread_id` handling) that must be preserved.
